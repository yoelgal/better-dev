# Releases

Machine-read by `/update`. One line per release, newest first:
`<version> <flags> - <summary>`, where `<flags>` is a comma-joined subset of
`install,reonboard,offer`. Four tiers: **pull-only** (the default - `git pull` in the clone is the
whole update), **install** (a skill dir was added, removed, or renamed - re-run `install.sh` once
per machine), **reonboard** (a repo surface changed - re-run `/onboard` once per wired repo), and
**offer** (the release added something opt-in - ask the operator once whether they want it). A
version with no line here is pull-only; flags are never empty. One line covers everything in its
release, so its flags are the **union** of what each change in it needs, never the mildest one: a
release that changed a repo surface *and* removed a skill dir is `install,reonboard`, because
dropping the `install` tier leaves a dangling link to a deleted skill on every machine and no nudge
ever fires for it. A line that removes or renames a skill also names where its job went - the skill
that absorbed it, or "retired, nothing replaces it" - since the installer prunes the link silently
and the operator's next question is what to reach for instead.

The first three tiers say *do this to stay current*; `offer` is the only one that asks a question,
and it exists because a new capability otherwise reaches new installs alone. A first install meets
an opt-in capability at its own front door (`BOOTSTRAP.md`); an already-wired machine never runs
that again, so without this flag the capability ships invisible to every existing user. `/update`
collects pending `offer` flags exactly like the other two and puts each summary to the operator as
a one-time question; the `wired-version` stamp closes it, so a declined offer is not re-asked.

**An `offer` line always carries `reonboard` too.** An offer is collected when a wired repo runs
`/update`, and the reonboard tier is what tells the operator that a repo owes that run at all - an
offer without it waits on a run nobody was told to make. The package gate enforces the pairing.

0.16.0 install,reonboard - **better-dev deletes every part of itself the harness already does, and 40,000 lines go with them.** 357 files become 149. Gone: the guard (`scripts/bd-guard`, its omp bridge, and the two `PreToolUse` entries) replaced by omp's own `bash.patterns`, whose `deny` and `prompt` rules fire on any segment of a compound line and whose `allow` rules never vouch for one, which is the bug class the hand-rolled version kept reopening; the memory CLI (`scripts/bd-mem`, 1,208 lines) replaced by `memory.backend`, `memory://root/learned.md` and the `learn` tool; a 32,364-line Playwright project replaced by the native `browser` tool; the code-graph wrapper and its six skills replaced by `lsp` references and definitions; the awareness hooks and host adapters replaced by the host auto-loading `CLAUDE.md` and resolving skills itself. `orchestrating-agents/tiers.md` folds into native model routing (`modelRoles`, `task.agentModelOverrides`, `@smol`/`@slow`, `prewalk`). The vendored `ios-qa/` daemon is fetched from upstream on demand instead of shipped. **This release owes you one command: `git pull` in your clone, then re-run `install.sh` once per machine.** That is not the usual link refresh. Until now the installer registered hooks by absolute path into your clone, and a pull deletes their targets, so Claude Code fails a hook on every session start and omp logs a module load error on every session - forever, because the code that wrote those entries is gone with the pull too. The installer carries a one-time migration that removes them, drops the stale `.better-dev/bin` permission allowances, and prunes the nine dropped skills' links, keeping any foreign hook in the same event and backing up `settings.json` first. It is idempotent and silent on a clean machine. Then `/onboard` per wired repo, which now writes a committed `.omp/config.yml` carrying your destructive-command policy. **One capability is deliberately lost, not replaced:** the guard also gated edits by path (`.env*`, `**/secrets/**`, `*.pem`, `*.key`), and `tools.approval` keys on tool name only, so nothing mechanically refuses a write to those paths any more. It was advisory rather than a boundary, and on omp it was already inert because the confirm it opened was invisible to the operator. Your recorded lessons and papercuts are untouched on disk; export them through `learn` if you want them in the native store.

The new skills: **`/deep-research`** (a sourced answer carrying its provenance, where no research capability existed at all), **`/prototype`** (settle a decision by building something throwaway, the verdict recorded and the code left out of the tree), **`/test-audit`** (mutation-settled findings on the suite that passes against broken code), **`/session-review`** (the trigger the memory store never had), **`/vision`** (recover an existing repo's intent into a `VISION.md` acceptance policy), **`/pick-ui-library`** (the decision procedure, naming no package as the answer), **`/human-review`** (anchored markup on a rendered artifact) and **`/brief-to-problem`** (somebody else's adjective decoded before it gets planned). Among twenty changed skills: `/review` gains a FIX/NIT/ESCALATE disposition beside severity and a convergence stop with a cap; `/security-pass` gains a five-check evidence gate and **deletes** our flat "env vars and CLI flags are trusted" precedent, since that trust rested on the writer already holding shell access and a CI parameter another team writes has writers who hold none of it; and the loop's first green now also runs the recorded `verify` once, so a work-item can no longer redden a different suite and still settle DONE for CI to find later. All 167 traps carry a typed result field, 166 of them reading `Last run: never` rather than leaving the fingerprint to imply a validation nothing evidenced. **What you owe: `git pull` in your clone, then re-run `install.sh`** so the eight new skills are linked on this machine, **then `/onboard` per wired repo** to refresh the discovery block's routing rows and the rewritten comms block. If you carry the comms block machine-wide in your host's global entry file (the 0.9.0 offer), that copy sits outside every repo and `/onboard` skips it there: run `/update` for the drift report and refresh it from `docs/comms-block.md`.

0.14.0 install - **better-dev installs for omp (Oh My Pi).** A fourth host adapter: `./install.sh` now detects omp, links your skills into its native dir, and registers the awareness hooks there. Two things made this more than a copy of the Claude adapter. omp has **no command-hook config at all** - `SessionStart`, `SubagentStart` and `PreToolUse` do not exist in it, and its hooks are TypeScript modules - so the hooks ride a bridge module that runs the same `bd-*` scripts unchanged, with per-worker re-injection on the `task` tool since omp exposes no subagent-spawn event. And omp's hook discovery **silently skips symlinks**, which is why the bridge installs as a real stub that re-exports from your clone: it loads, and `git pull` still refreshes it. `install.sh --verify` stopped grepping file content and now asks the host's own wiring script, which closes a hole it already had for Claude - the old grep passed while a newly added hook was missing. The session-start nudges are host-scoped too, so the link and hook nudges answer for whichever host invoked them instead of always for Claude Code; one consequence reaches Claude users, where a machine with skills linked and no `settings.json` at all now gets the hookless-install nudge it was silently skipping. **Re-run `install.sh` once per machine** to pick omp up. Not covered yet, and named rather than implied: `bd-guard`'s blast-radius hooks are not wired for omp, and a named omp profile relocates both directories.
